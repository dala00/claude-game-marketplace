# new-adventure — アドベンチャーゲーム作成スキル（作者向け）

ユーザーが「新しいアドベンチャーゲームを作りたい」「このパターンの推理ゲームを追加して」等と言ったら、このスキルの手順で 1 本のゲームプラグインを構築する。

**このスキルは開発作業用。** プレイ用スキル（各ゲームの `skills/play/SKILL.md`）とは別物。完成物の `play` スキルがゲーム本体になる。

参考実装: `plugins/mini-adventure`（線形短編）、`plugins/snow-lantern-mystery`（推理・捜査ハブ型）。ファイル形式・注意書きの書き方は後者を雛形として読むとよい。

**推理ものを作るなら、設計に入る前に `structure.md`（このスキルディレクトリ内）を必ず読む。** 初期 4 作は一段構成で「あっさり終わる」問題があり、`structure.md` はその処方——五幕・二山構成、中間推理と見立ての崩壊、追及（対決）パート、人物の三層化、ボリューム基準——をまとめた必読資料。既存作を雛形にすると一段構成をそのまま複製してしまうので、**構成は `structure.md`、書式は既存作**という使い分けをする。

---

## このアーキテクチャの核心（最重要 — これがこのパターンの肝）

**ネタバレを構造で防ぐ。** 物語を `story/` 配下の複数ファイルに分割し、プレイ用スキルの進行役（AI）が**指示されたファイル以外を絶対に読まない**規約で動く。これにより、進行役自身が結末や真相を「知らない」状態でプレイを進められ、うっかり先のネタバレを漏らすことが構造的に起きない。

- 現在のシーン／場所のファイルだけを手元に持ち、そこに書かれた**遷移条件**に従って次のファイルを Read する
- 真相・結末ファイル（例: `truth.md`、最終シーン）は、**プレイ上その情報が解禁される瞬間まで進行役も読まない**
- 各ファイル末尾に必ず **「注意（AI 厳守）」** セクションを置き、「ここに書かれていないことを捏造しない」「指定ファイル以外を読まない」を明記する

この原則を、生成する全ファイルとプレイ用 SKILL.md に必ず織り込む。

## 作成手順

### ステップ 0 — 形式を決める

ユーザーと相談して、どちらの型かを決める:

- **線形型**（mini-adventure 系）: 一本道でシーンが進む。謎解き／脱出／心理劇向き。ファイルは `story/<scene>.md` の連鎖
- **捜査ハブ型**（snow-lantern-mystery 系）: 自由探索パートを持つ。推理もの向き。ハブファイルを台帳に `areas/` `people/` を行き来し、終盤に解決編＋真相ファイル

以下は両対応で書く。**推理ものは捜査ハブ型一択**で、その具体構成は `structure.md` の「五幕・二山構成」に従う（第二章の初動捜査 → 中間推理 → 第三章の再捜査と追及 → 解決編 → 決着）。一段構成（顔合わせ→捜査→解決）は採らない。

### ステップ 1 — 全体設計を作り、ユーザーに見せて確認を取る

**いきなりファイルを書かない。** まず設計を固め、概要を提示して合意を得る。推理ものの設計順序（snow-lantern-mystery で確立したもの）:

1. **舞台**（場所・時代・状況。「閉ざされた空間」は王道で扱いやすい）
2. **主人公**（＋必要ならパートナー／同行者）。職業・視点・なぜ事件に関わるか
3. **大きな流れ**（犯人・犯人の背景・トリック・必要な証拠品・関係者）
4. **エリア設定**（建物なら部屋、野外なら区画）
5. **人物配置**（各人がいつどこにいたか。タイムライン表を作る）
6. **二山の設計**（推理ものは必須。`structure.md` 参照）
   - **第一の見立て**: 第二章の証拠が指し示すミスリードの解。誰が疑わしく見えるか、なぜそれが崩れるか
   - **第三章の引き金**: 第二の事件／物証の隠滅／偽の自白／外部からの期限／立場の反転のどれか 1 つ
   - **対決 3〜5 個**: 誰の・どの嘘を・どの証拠で崩すか。**うち 2 つ以上は無実の人物の秘密**にする
7. **全員の隠し事と沈黙の理由**（犯人を含む全員に 1 つずつ。犯人の隠し事は「殺したこと」以外にする）
8. **主人公の縦糸**（私的な事情を 1 本。章の切れ目に差し込み、エピローグで回収する）

設計ができたら**概要をまとめてユーザーに提示**し、変えたい点を聞く。**タイトルは最後に決める**。

設計時の注意:
- **タイムライン表を必ず作る**（時刻 × 出来事 × 各人の所在）。後の矛盾チェックの土台になる
- 推理ものは**ミスリード要員**（偽の動機を持つ別の容疑者）を 1〜2 人入れると面白くなる
- 「面白かった！」と思える起伏（どんでん返し・感情の落とし所）を設計段階で決めておく。**山は 2 つ作る**——中間推理での見立てと、その崩壊。これが「あっさり」への最大の対策
- **人と場所は増やさず、一人あたりを深くする。** 容疑者を 8 人にするより、5 人に層 1・層 2・層 3（隠し事）とサブプロットを持たせるほうが濃く面白くなる。ボリュームの目安は `structure.md` の表を見る
- **容疑者は 5 人以下を目安に絞る。** 全員に「肩書き＋見た目か口癖の一点」のタグを付け、初登場時に必ずセットで描く（例:「いつも飴を噛んでいる管理人」）。人数を増やすより一人ひとりの覚えやすさを優先する
- **第一幕は 1 シーンに人物を詰め込まない。** 新顔 1〜2 人ずつが登場する小シーン 4〜6 個に分け、主人公が小さな用事や仕事をこなしながら自然に顔合わせし、その途中（または直後）に事件が起きる構成にする。「開幕即・全員集合→次のシーンで事件→探索開始」の駆け足を避ける
- **事件の衝撃を設計する**（`structure.md` の「第一章の設計」参照）。被害者との「最後のあたたかい場面」、書かれた予兆 2〜3 個と直前の静けさ、そして発見シーンの専用ファイル化——発見〜依頼を 1 塊のナレーションで流さず、戸を開けるのはプレイヤーの入力で起こす

### ステップ 2 — ファイルを生成する

ディレクトリ構成（`<game-name>` は kebab-case）:

```
plugins/<game-name>/
  .claude-plugin/plugin.json
  skills/play/SKILL.md            # プレイ用スキル。name: play で統一（CLAUDE.md 必須ルール）
  skills/play/story/
    # 線形型はここだけ:
    <opening>.md → 中間シーン → <final>.md

    # 捜査ハブ型（推理もの）の標準構成 — 詳細は structure.md
    act1_*.md × 4〜6              # 第一章 導入（用事つきの小シーン→予兆→事件）
    act1_discovery.md             # 遺体発見（2〜3 ターンに割る。structure.md 2-3）
    act2_hub.md                   # 第二章 初動捜査の台帳
    areas/*.md                    # 場所（第二章で見えるもの）
    people/*.md                   # 人物（層 1・層 2）
    act2_end.md                   # 中間推理（正誤判定をしない。truth.md を読まない）
    act3_incident.md              # 第三章の引き金。見立てが崩れる
    act3_hub.md                   # 第三章 再捜査の台帳（act2_hub.md は以後読まない）
    areas_b/*.md                  # 見え方が変わる場所＋第三章で解禁される場所
    people_b/*.md                 # 更新された証言
    confront/*.md × 3〜5          # 追及（対決）。層 3 の隠し事はここにだけ書く
    act4_deduction.md             # 解決編
    truth.md                      # 真相（解決編の判定手順まで誰も読まない）
    act5_confession.md            # 告白
    act5_motive.md                # 動機の掘り下げ
    act5_ending.md                # エピローグ（サブプロットと主人公の縦糸を回収）
```

**`confront/*.md` にも真相を書かない。** 対決で明かすのは「事実」だけで、意味づけと真相は `truth.md` に集約する。

- `plugin.json`: `name` / `version` / `description` / `author`（name: alphabrend）/ `keywords`
- `skills/play/SKILL.md`: **frontmatter `name: play` 固定**。本文に起動シーケンス・進行ループ・絶対ルール・ナレーション規約を書く。snow-lantern-mystery の SKILL.md をテンプレに流用してよい
- 絶対ルール（SKILL.md）とハブの注意には、次の 3 つを必ず含める（1・2 は既存 3 作の推理ものと同文でよい）:
  1. **「コア証拠」「フラグ」「移行条件」等の台帳用語・メタ区分をプレイヤーに出力しない**（証拠一覧表示でもコア印や残数を見せない）
  2. **ヒントで未獲得証拠の在処（場所・人物）を名指しで教えない**（獲得済みの証拠・証言からの遠回しな水向けまで。行き先はプレイヤーに選ばせる）
  3. **解決編より前に、地の文・NPC の証言で特定人物を断定的に疑わない・犯人を示唆しない**（演出上必要としてシーンファイルに書かれている場合を除く）。容疑の絞り込みはプレイヤー自身の発言にだけ反応する

### ステップ 3 — シーンファイルを書く（ネタバレ防止規約を守る）

各シーン／場所／人物ファイルの基本フォーマット:

```markdown
# <シーン名>

## ナレーション（そのまま提示する）
（プレイヤーに読み上げる地の文。常体・小説調）

## 調査ポイント / 自由行動（遷移なしの範囲）
（このシーン内で完結する応答。証拠獲得は「【証拠獲得: X】」で明示）

## 遷移条件（AI 用）
- プレイヤーが〜したら → `story/<next>.md` を Read して提示
- それ以外 → このシーンの範囲で短く応答して留まる

## 注意（AI 厳守）
- ここに書かれていない部屋・人物・物品・証言を捏造しない
- 指示されていないファイル（特に truth.md / 結末）を読まない
- （真相に触れる情報をこのファイルに書かない。容疑者は全員等しく扱う 等）
```

書くときの鉄則:
- **真相の直接記載は truth.md（または結末ファイル）だけに置く。** 中盤までのファイルには「事実・証言・物の状態」だけを書き、結論や意味づけを書かない（推理はプレイヤーがする）
- **人物ファイルは全員同じ温度で書く。** 犯人だけ描写を盛る・怪しく書くをしない。所作（手が止まる等）は書いてよいが意味づけはしない
- **NPC の証言・地の文に、特定人物を断定的に疑う表現を書かない。**「あいつが犯人に違いない」型の台詞は、ミスリード等の演出上の意図があってその場面に必要な場合のみ書いてよい（その際もファイルの注意に意図を明記する）
- **捏造の余地を塞ぐ。** 「この部屋にそれは無い」と言える範囲を各ファイルに明記
- 証拠フラグはハブ（捜査型）または進行で管理。入手先と条件を一覧化する
- **人物ファイルは三層で書く**（層 1 表の証言 / 層 2 条件つきの証言 /「層 3 は `confront/` にある」の記載）。全員が層 3 を持つので、その存在を書いてもネタバレにならない。1 人 60〜90 行を目安にする
- **場所はフェーズごとにファイルを分ける**（`areas/` と `areas_b/`）。1 ファイルに「第二章で見えるもの／第三章で見えるもの」を 2 段書きすると、進行役が先の情報を読んでしまう

### ステップ 4 — ナレーション規約を SKILL.md に明記する

プレイ用 SKILL.md の「ナレーションのスタイル」に必ず入れる:

- **常体・小説調**（「〜だ」「〜だった」）。ですます調のナレーション禁止（人物の台詞は除く）
- **語彙は「中学生が辞書なしで読める」を基準にする。** 雅語・専門語・時代がかった言い回しを乱用しない。固有名詞や演出上どうしても必要な語は使ってよいが、初出時に読みと意味がその場で分かるように添える
- **主人公（プレイヤー）の地の文での呼称を固定する。** 二人称（お前／あなた／君）を避け、**主人公の苗字**で呼ぶ（snow-lantern-mystery は「霧島」）。主語は省略してよいが明示時は苗字。台詞で呼びかけるときは「○○先生」等
- 1 ターン 2〜6 文程度。冗長な情景描写を避ける
- **1 ターンは語り手のナレーションで終え、そこで停止してプレイヤーの入力を待つ。プレイヤーの行動・台詞・次の入力を代筆して先に進めない**（`user` の発言を生成しない／ターン末の選択肢を自分で選んで続行しない）。線形型・捜査ハブ型の両方で必須。**この一文は生成する SKILL.md の「絶対ルール」にも必ず入れる**（モデルがプレイヤーの入力を肩代わりして自走する事故の防止。問いかけ調の選択肢スタイル自体は禁止しない）

### ステップ 5 — リポジトリに登録する（CLAUDE.md の必須手順）

1. `.claude-plugin/marketplace.json` の `plugins[]` に登録（name / source / description / category: "game" / tags）
2. **`README.md` の「収録ゲーム」セクションに、コピペ用のインストール／プレイ開始ブロックを追加**（利用者向け。開発情報は書かない）。フォーマットは CLAUDE.md と既存エントリに合わせる
3. プレイ用スキルの description は**利用者向けの導入文だけ**。実装ルールは SKILL.md 本文へ

### ステップ 6 — 到達可能性・整合性チェックを必ず行う

完成後、以下を検証する（snow-lantern-mystery で実施した QA と同等）:

1. **JSON 検証**: `node -e "JSON.parse(require('fs').readFileSync('<path>','utf8'))"` で plugin.json と marketplace.json をパース確認
2. **参照整合**: 全ファイル内の `story/...md` 参照が実在ファイルを指すか、孤立ファイルがないかをクロスチェック（Grep で `story/[\w/\-]+\.md` を集めて Test-Path）
3. **到達可能性**: すべての証拠フラグ／シーンにプレイヤーが普通に辿り着けるか。ゲート（鍵・解禁条件）がデッドロック／循環していないか
4. **解決可能性**（推理もの）: truth.md の判定基準が、プレイヤーが入手できる情報だけから論理的に導けるか。情報不足がないか
5. **矛盾チェック**: タイムライン表と各ファイルの記述（時刻・所在・証言・物の配置）を突き合わせる
6. **ネタバレ防止構造**: 中盤までのファイルだけで真相が進行役に確定しないか。各ファイルに「注意（AI 厳守）」があるか
7. **構成チェック**（推理もの）: `structure.md` 末尾の「設計チェック」10 項目を上から順に潰す。特に——第二章だけで真相が証明できないこと、中間推理がどの回答でも先へ進むこと、対決の 2 つ以上が無実の人物の秘密であること、全対決を突破しなくても第四章へ行けること
8. **ボリューム確認**: `find story -type f | wc -l` と `wc -l` で `structure.md` の基準（34〜42 ファイル／2,200〜3,000 行）と突き合わせる。届かないときは文章を水増しせず、対決・層 2 の証言・サブプロットのどれが欠けているかを疑う

**規模が大きい場合は Agent（general-purpose / Explore）に全ファイルを読ませて独立監査させると漏れが減る。** 検出した問題は重大度（致命的＝進行不能・推理不能／中＝矛盾／軽微＝表現）を付けて修正する。
